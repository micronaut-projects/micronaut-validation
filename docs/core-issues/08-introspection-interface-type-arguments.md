# A bean introspection does not record the type arguments a bean binds in its interfaces

**Component:** `micronaut-core` — `core` (`BeanIntrospection`), `core-processor` (`BeanIntrospectionWriter`)
**Found on:** micronaut-core `5.2.0-SNAPSHOT`, measured from micronaut-validation `reflection-behind-seam-wip`
**Unblocks:** 24 tests of `micronaut-validation`, and the last reflective read the validator cannot remove

The index of these files lives on `claude/core-reflection-bridge-docs`; this one is filed from the branch
that found it.

## Summary

`BeanDefinition` records what a bean binds the type arguments of a super type to.
`BeanIntrospection` records nothing of the kind, and `getGenericBeanType()` carries only the type
parameters the bean type itself declares. So a lookup keyed by a bare `Class` can learn what the type binds
only if that class happens to be a container bean.

## Evidence

For one class, generated by the Java annotation processor with both `@Introspected` and `@Singleton`:

```java
@Introspected
@Singleton
class Test implements ConstraintValidator<NotNull, CharSequence> {
    public boolean isValid(CharSequence value, AnnotationValue<NotNull> ann, ConstraintValidatorContext ctx) {
        return true;
    }
}
```

| Call | Result |
| --- | --- |
| `definition.getTypeArguments("…constraints.ConstraintValidator")` | `[NotNull A, CharSequence T]` |
| `definition.getTypeArguments()` | `[]` |
| `introspection.getGenericBeanType().getTypeParameters()` | `[]` |
| `introspection.asArgument().getTypeParameters()` | `[]` |

The named `BeanDefinition` overload has exactly the answer. Nothing on the introspection does.

The no-argument `getTypeArguments()` returning empty while the named overload returns the arguments is a
second oddity worth confirming. It may be intended to mean the first generic super type rather than any
interface, in which case only the documentation is at fault.

## Why it matters

Jakarta Validation picks the `ConstraintValidator` for a value by the second type argument of
`ConstraintValidator<A, T>`. micronaut-validation has to answer that from a bare `Class` in three places,
and in none of them is a `BeanDefinition` at hand:

- `ConstraintValidatorTargetResolver.resolve`, over the classes a constraint's `@Constraint(validatedBy)`
  names. These are class literals on an annotation, not beans.
- `DefaultValidatorConfiguration`, checking that a validator class a user-supplied
  `jakarta.validation.ConstraintValidatorFactory` returns is compatible with the value.
- `DefaultInternalConstraintValidatorFactory`, for a validator the container does not build and
  instantiates through its declared constructor.

Today each falls back to reading the class's generic interfaces. That is the last reflective read
micronaut-validation cannot replace with generated metadata, and it is what keeps
`micronaut-validation` dependent on `micronaut-validation-reflection` for ordinary validator resolution.
Removing the reflective fallback leaves 24 of the module's own 534 tests unable to resolve a validator.

## The three scenarios

| The validator is | Answerable today | By what |
| --- | --- | --- |
| a container bean | yes | `BeanDefinition.getTypeArguments(String)` |
| introspected but not a bean | no | nothing |
| neither | no | only reading the class |

The first is answerable in principle but not at the call sites above, which hold a `Class` and no context.
The second is the gap this issue asks to close: the metadata is generated for the same class as a bean
definition and withheld from the introspection. The third is the honest boundary, and the reflection module
is the right answer for it.

## What to implement

Mirror the `BeanDefinition` accessor on `BeanIntrospection`:

```java
List<Argument<?>> getTypeArguments(Class<?> type);

List<Argument<?>> getTypeArguments(String type);
```

written by `BeanIntrospectionWriter` from the same resolution `BeanDefinitionWriter` already performs, so
that an introspected type answers what it binds in a super type without a bean definition and without
reading the class.

## Tests to add

- an `@Introspected` class implementing a generic interface with both arguments bound reports them from
  `getTypeArguments(Class)`, and reports the same list the bean definition reports for the same class
- a class binding through an intermediate interface (`A implements B`, `B extends Iterable<String>`)
  reports `String`
- a class leaving an argument open (`Any<T> implements ConstraintValidator<NotNull, T>`) reports the
  variable rather than a resolved type, matching what `BeanDefinition` does
- an `@Introspected` class implementing no generic interface reports an empty list rather than throwing

## Workaround in the meantime

micronaut-validation annotates the validators it owns with an internal `@ConstraintValidatorTypes`, carrying
the constraint and the target, and reads it from the introspection. Its own annotation processor writes that
for user validators, but it cannot be run over `micronaut-validation` itself, because the processor depends
on the module, so the six built-in validators declare it by hand. Closing this issue removes the annotation,
the hand declarations and the processor visitor that writes it.
