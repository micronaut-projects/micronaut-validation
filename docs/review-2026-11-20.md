## High

### 1. Executable plan cache reuses another implementation's constraints (S, A)
- `IntrospectedExecutable.java:100`, `ValidatorDeclarations.java:175`
- `IntrospectedExecutable.equals`/`hashCode` compare only the `Method`, and `executablePlan` first looks up `methodPlans` by that executable, before the declaring type is resolved.
- Scenario: two introspected implementations of `Lookup.find()`, only the second with `@NotNull` on its return (A), or with `@Size(min = 1)` and `@Size(min = 5)` respectively (S). Validate the first through `Lookup.class.getMethod("find")`, then the second through the same `Method`: the first implementation's plan is used, and the null or short value passes.

### 2. Interface group sequence containing `Default` is rejected (S, A)
- `GroupSequences.java:157-159`
- `expandGroup` throws for `Default.class` in any sequence. The spec forbids `Default` only in a class that redefines its own default sequence.
- Scenario: `@GroupSequence({Default.class, Detailed.class}) interface Complete {}` and `validate(bean, Complete.class)` throws `GroupDefinitionException`. Both codex reviewers cite spec example 5.10 for this pattern.

### 3. A failing sequence step stops later requested groups (F, S, A)
- `ValidationTraversal.java:176`, `DefaultConstraintValidatorContext.java:352`, steps built in `GroupSequences.java:219-237`
- The requested groups are flattened into one step list, and the loop `break`s on the first failed sequence step.
- Scenario: `validate(bean, FirstThenSecond.class, Other.class)` with both `first` and `other` invalid reports only `first`. With two sequences, the second is skipped entirely. `ReviewFindingsTest.aSequenceAfterAnotherGroupStopsAtItsFirstFailingGroup` only covers the order `Other, Sequence`, so the result depends on argument order.

### 4. `@UnwrapByDefault` extractor replaces the whole extractor list (S, A)
- `ValidationTraversal.java:571-573`, `validation-jakarta/.../JavaFxValueExtractors.java:63`
- When more than one extractor applies, the list is replaced by the single unwrap-by-default extractor.
- Scenario A: `Pair<String, @NotNull String>` with separate extractors per slot, where only the left one unwraps by default. A null right value passes.
- Scenario S: `@Valid ListProperty<Child>` with an invalid child. The value is unwrapped to the backing list and cascades into the list object, so the child violation is lost.

### 5. `messageTemplate(...)` bypasses the custom-violation EL restriction (F high, S medium)
- `ConstraintEvaluator.java:255-259`, `validation-el/.../ElMessageInterpolator.java:211-213`
- A template set with Micronaut's `ConstraintValidatorContext.messageTemplate(String)` is interpolated with `customViolation=false`.
- Scenario: a validator does `context.messageTemplate("invalid [" + value + "]")`, as the repo's own `test-suite/.../PatternValidator.java:29` does, with the EL module present. The input `${validatedValue.length()}` or a stream expression is fully evaluated, whereas the same text through `buildConstraintViolationWithTemplate` stays literal. No test covers this.

### 6. `formatter.format` in "variables only" templates allows heap exhaustion (F medium, A high)
- `validation-el/.../ElMessageInterpolator.java:345-385` (exemption at 366 and 376), output at 452
- Any `formatter.format(<literal>)` passes the variables-only check, and the formatter's output is not bounded.
- Scenario: user text reaches `buildConstraintViolationWithTemplate`, and the value is `${formatter.format('%2000000000%')}`. F confirmed with a scratch program that `%50000000%` produces 50M characters. The resulting `OutOfMemoryError` is not caught by the `RuntimeException` handler at line 331.

### 7. Kotlin `suspend` methods validate the coroutine marker (F, unverified)
- `validation/.../ValidatingInterceptor.java:160-174`
- The `COMPLETION_STAGE` branch now calls `context.proceed()` instead of `interceptResultAsCompletionStage()` as on 5.3.x, so a suspend function's return value, or `COROUTINE_SUSPENDED`, is validated directly.
- Scenario: `@NotBlank suspend fun name(): String { delay(1); ... }`. When it suspends, `ClassCastException` on the marker becomes a `ValidationException` while the coroutine is still running. With `@NotNull`, the real value is never checked. No test uses `suspend`.

### 8. Group conversion to a sequence re-applies the conversion (S)
- `GroupSequences.java:135`, `:161`
- The recursive expansion keeps the conversion map for each member of the target sequence.
- Scenario: `@Valid @ConvertGroup(from = A.class, to = Seq.class)`, where `Seq = [A, B]`, validated in `A` throws `GroupDefinitionException` (cyclical) instead of checking the child in `A` and then `B`.
- This conflicts with F's note that `convertGroups` is idempotent per relationship. That note concerned chained conversion, not expansion of a sequence target, so this one needs a test.

### 9. XML field mapping erases getter constraints (S)
- `validation-xml/.../XmlBeanIntrospector.java:121`, asserted by `XmlBeanIntrospectorTest.java:301`
- The XML introspector replaces the whole property when a mapping names either the field or the getter.
- Scenario: with bean-level `ignore-annotations="false"`, `<field name="name" ignore-annotations="true"/>` also drops `@NotNull` on `getName()`. Spec §9.1.1.2–3 keeps the two members separate.

### 10. XML validator overrides lost inside composed constraints (A)
- `DefaultConstraintDescriptor.java:619`, `:634`
- Child descriptors of a composed constraint are built with a null validator override, on both the generated and the reflective path.
- Scenario: XML replaces the validator of `@Code` with a stricter one. `@ProductCode`, which is composed of `@Code`, still uses the original validator and accepts the value, and its descriptor reports the original validator classes.

## Medium

### 11. Mapping XML is not validated against the XSD (S, A)
- `validation-xml/.../XmlMappingParser.java:125-126`, `:600`. Only `ValidationXmlBootstrapConfigurationLoader.java:148` validates against a schema.
- `addMapping(<wrong-root/>)` succeeds as an empty mapping (A). Two `<message>` children are accepted, and the second one wins (S). Parsing itself is secure (F): DOCTYPE is disallowed and external entities, XInclude and external schema access are off.

### 12. Metadata group matching does not expand sequences (S, A)
- `IntrospectedBeanDescriptor.java:280`, `:573`; `IntrospectedExecutableDescriptors.java:185-191`
- `findConstraints().unorderedAndMatchingGroups(Ordered.class)`, with `Ordered = [Basic, Detail]`, omits `@NotNull(groups = Basic.class)`, although validating `Ordered` runs that constraint.

### 13. `@ReportAsSingleViolation` evaluates every composing validator (S, A)
- `ConstraintEvaluator.java:234`
- After the first failure, the remaining composing validators still run. Two failing validators with a shared counter count to 2, and a later validator that throws turns a determined violation into a `ValidationException`. Whether the spec requires stopping early is arguable, since §3.3 only fixes the report, but the throwing case is a real behaviour difference.

### 14. Static `AnnotationValueCache` retains class loaders and thrashes (F, S, A)
- `constraints/AnnotationValueCache.java:36-62`, `constraints/ConstraintMembers.java:33`, `AbstractPatternValidator`, fed by `validation-xml/.../XmlMappingParser.java:787-790`
- The cache uses static strong identity keys on whole `AnnotationValue`s, up to 1024 per cache. An XML-mapped `@Size` whose groups come from a child loader keeps that loader alive after the factory closes, in a shared-parent deployment (S, A). An application with more than 1024 distinct occurrences clears the whole cache on every overflow (F, line 58).

### 15. Container element constraint forces the declared-type extractor (S)
- `ValidationTraversal.java:521`, `extractors/InternalValueExtractors.java:68`
- `Iterable<@NotNull @Valid Child>` holding a `List` cascades through the `Iterable` extractor and reports the child with a null index instead of `0`.

### 16. Executable validation argument checks (S, A)
- `DefaultExecutableValidator.java:93`, `:236`, `:341`
- Unconstrained parameters are not type-checked: `validateParameters(bean, save(String), new Object[]{42})` returns an empty set (A). A null argument array is normalised to an empty one before the arity check, so `validateConstructorParameters(noArg, null)` passes (S). The API requires `IllegalArgumentException` in both cases.

### 17. Un-introspected `@GroupSequence` silently treated as a plain group (F)
- `GroupSequences.java:149-155`, related to `CompileTimeSupport.java:339`
- A sequence interface from a jar compiled without the 5.3 processor, used without the reflection module, falls back to an empty sequence. Validation then runs in a group no constraint belongs to and returns no violations for an invalid bean. Inherited group conversion raises `reflectionRequired` in the equivalent situation.

### 18. Method-hierarchy rules now enforced at call time, undocumented (F)
- `DefaultExecutableValidator.java:127` calling `ExecutableHierarchy.java:261-300`; the gap is at `ExecutableHierarchy.java:141-144`
- A parameter constraint added in an override now throws `ConstraintDeclarationException` on every call, where 5.3.x validated it. For example, an `@Introspected interface Api { void m(String s); }` implemented as `void m(@NotBlank String s)`. This is missing from `breaks.adoc`. It is also uneven: when the super type has no introspection, the same violation goes undetected.

### 19. Bare `${attribute}` renders as `$<value>` (F)
- `validation-el/.../ElMessageInterpolator.java:205-210`, asserted by `ElMessageInterpolatorTest:147`
- `@Min(value = 5, message = "must be ${value} at least")` gives "must be $5 at least", while the reference implementation gives "must be 5 at least". This is deliberate, but it contradicts the spec's mapping of attributes to EL variables and is not in `breaks.adoc`.

### 20. XML boolean `1` read as false (A)
- `validation-xml/.../ValidationXmlBootstrapConfigurationLoader.java:133`, `XmlMappingSupport.java:115`
- `Boolean.parseBoolean` is used, so `<executable-validation enabled="1"/>` disables executable validation, and `ignore-annotations="1"` keeps annotations active.

### 21. Filtered property finder is inconsistent (A)
- `IntrospectedBeanDescriptor.java:443`
- `findConstraints().unorderedAndMatchingGroups(Audit.class)` on a property with only a default-group `@NotNull` returns `hasConstraints() == true` with an empty descriptor set. The existing test (`ValidatorSpec.groovy:1028`) covers only the class-level finder.

### 22. Strict definition check accepts `List<Object>` validators (A)
- `validation-processor/.../ConstraintDefinitionMetadata.java:155`, `validation-reflection/.../ReflectedConstraintDefinitions.java:186`
- A type argument that resolves to `Object` is treated as `?`, so `ConstraintValidator<C, List<Object>>` passes and can be chosen for a `List<String>` property.

### 23. Null context component drops the factory's component (A)
- `DefaultValidatorFactory.java:271`, `DefaultValidatorConfiguration.java:260`
- `factory.usingContext().clockProvider(null).getValidator()` uses the provider's default clock instead of the factory's. The `ValidatorContext` contract says null restores the factory's component.

### 24. `addProperty(name, null)` crashes factory creation (A)
- `validation-bootstrap/.../MicronautValidatorConfiguration.java:215`, `:375`
- The null value is stored, and `Map.copyOf` then throws `NullPointerException` when the factory is built.

### 25. Reflection companion bypasses generated attribute readers (S)
- `validation-reflection/.../ReflectionValidationSupport.java:373`, `RuntimeValidationAccess.java:104`
- When the companion is installed, a processor-generated constraint with an enum member is read through reflective member lookup and invocation on every interpolated failure.

## Low

### 26. `validateProperty`/`validateValue` diverge from `validate` (F)
- `DefaultValidator.java:258-266`, `:291-300`
- Neither method calls `declarations.checkBeanDeclarations` or applies isolated super-type default sequences. `validateValue` also reads `beanProperty.getAnnotationMetadata()` directly, bypassing the per-member plans. The practical effect is unverified.

### 27. Other retaining caches (F)
- `DefaultValidator.java:361`: unbounded `beanDescriptors`, including `EmptyDescriptor`s, for every class probed.
- `DefaultValidatorFactory.java:315`: a static `Cleaner` thread that is never stopped.
- `validation-xml/.../XmlMappingSupport.java:140`: the static `SCHEMAS` map, bounded today only because the version is checked first.

### 28. Hot-path costs (F)
- `ValidatingInterceptor.java:160-166`: every `CompletionStage` method runs `validateReturnedContainer` even when `plan.returnValueValidated()` is false.
- `ConstraintEvaluator.java:104-109`, `:370`: two `ThreadLocal` lookups, a `LongAdder` update and a path scan per element.
- `ElMessageInterpolator.java:164`, `:301`: the attribute map is rebuilt per message and per expression.
- `DefaultExecutableValidator.java:351`: `isConvertibleToPublisher` is checked per parameter per call.

### 29. `@Digits` integer-length overflow (F, pre-existing)
- `constraints/DigitsValidator.java:58`
- `"1E2147483647"` passes `@Digits(integer = 3, fraction = 0)` because `precision() - scale()` overflows to `-2147483648`. The reference implementation has the same behaviour.

### 30. `validatedAnnotatedElement` drops constraints for null (F, pre-existing)
- `DefaultValidator.java:321`
- A null value is validated against `Argument.OBJECT_ARGUMENT`, so an `@NotNull` element yields no messages.

### 31. Missing `@since` on `MicronautValidatorContext.addValueExtractor(ValueExtractorDefinition)` (S)
- `MicronautValidatorContext.java:70`

## Checked and found sound (F)

- Secure XML parsing, and a `ValidationException` for multiple `validation.xml` files.
- No chained group conversion.
- The close/validate race in `ConstraintValidatorInstances`.
- `@ReportAsSingleViolation` de-duplication.
- New public types carry `@since 5.3.0` and, apart from `MicronautValidatorContext`, are `@Internal`. Public interfaces only gained default methods. A compares public and protected signatures against the released 5.2.1 jars and found no removals. japicmp was not run.

- Benchmarks.
- F did not read `validation-processor`, most of `validation-reflection`, `validation-jakarta`, or `ValidationPath`. S and A covered those modules only at source level.
- Exhaustive Java/Groovy/Kotlin processor parity, and an exhaustive `@since` audit.
- The untracked `ContainerIndexOverrideTest.java` was excluded, as requested.
