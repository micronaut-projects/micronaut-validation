Micronaut Validation separates the default lightweight validator from the optional Jakarta Validation compliance stack.

The default dependency is appropriate for most Micronaut applications:

dependency:micronaut-validation[groupId="io.micronaut.validation"]

It validates using Micronaut introspection and compile-time metadata. It does not enable XML parsing, Jakarta EL interpolation, ServiceLoader bootstrap, or reflection fallback by default.

== Jakarta Compliance Dependency

Use the aggregate module when an application, test suite, or library needs the Jakarta Validation provider bootstrap or other specification-oriented behavior:

dependency:micronaut-validation-jakarta[groupId="io.micronaut.validation"]

The aggregate pulls in the optional modules that make up the Jakarta compliance stack.

== Module Model

`micronaut-validation`::
The default lightweight validation implementation. It uses generated annotation metadata and bean introspections and remains free of XML, Jakarta EL, reflection fallback, and `jakarta.validation.spi.ValidationProvider` ServiceLoader registration.

`micronaut-validation-bootstrap`::
Provides the Jakarta `ValidationProvider`, `Configuration`, and `ValidatorFactory` bootstrap integration used by `jakarta.validation.Validation`.

`micronaut-validation-reflection`::
Adds optional reflection fallback for specification behavior that cannot be satisfied from generated Micronaut metadata alone.

`micronaut-validation-xml`::
Adds support for `META-INF/validation.xml` and Jakarta constraint mapping XML resources.

`micronaut-validation-el`::
Adds Jakarta EL message interpolation, backed by https://github.com/micronaut-projects/micronaut-expression-language[Micronaut Expression Language].

`micronaut-validation-el-processor`::
An annotation processor that compiles the Jakarta EL expressions of the constraint message templates at compilation time.

`micronaut-validation-jakarta`::
Aggregates bootstrap, reflection, XML, and EL support for the Jakarta compliance stack.

== Choosing Modules

Prefer `micronaut-validation` when you want Micronaut's compile-time validation model and GraalVM-friendly defaults.

Use `micronaut-validation-jakarta` when you need Jakarta Validation bootstrap behavior, XML configuration, constraint mapping XML, Jakarta EL interpolation, or reflection fallback for specification compatibility.

You can also depend on individual optional modules when only one part of the compliance stack is required.

== Jakarta EL Message Interpolation

The section 5.3.1.1 of the specification lets a constraint message contain Jakarta EL expressions:

[source,java]
----
@Size(min = 1, max = 8, message = "the title is ${validatedValue.length()} long, not between {min} and {max}")
private String title;
----

`micronaut-validation-el` evaluates them with
https://github.com/micronaut-projects/micronaut-expression-language[Micronaut Expression Language], an
implementation of Jakarta Expression Language 6.0 whose expressions are generated at compilation time. Property
access goes through the bean introspections rather than through the reflective `jakarta.el.BeanELResolver`.

=== Compiling the Expressions

A constraint message is a compile-time constant, so the expressions it contains are known before the
application runs. Add the processor to compile them:

dependency:micronaut-validation-el-processor[groupId="io.micronaut.validation",scope="annotationProcessor"]

For every type declaring a constraint, the processor runs the message parameter pass of the specification over
the template, compiles the expressions that remain, and registers them as an `ELExpressionSource`. The
interpolator then receives a generated `jakarta.el.ValueExpression` instead of parsing the string on every
violation. `${validatedValue.length()}` becomes:

[source,java]
----
public final class Book$ValidationExpression0 extends CompiledValueExpression {

    protected Object evaluate(ELContext context) {
        return ELResolution.invoke(context,
            ELResolution.resolveIdentifier(context, "validatedValue"), "length", new Object[]{});
    }
}
----

=== Expressions Built at Runtime

An expression the processor did not compile — one coming from a message template built at runtime, or from a
resource bundle chosen by the locale of the request — needs the interpreter:

dependency:micronaut-expression-language-interpreter[groupId="io.micronaut.el",scope="runtimeOnly"]

`micronaut-validation-jakarta` declares it, so the compliance stack has it by default. Without it, an
uncompiled expression is left in the message as it was written.
