Micronaut Validation 5.3 requires Micronaut core 5.3 or later. Development uses the matching core 5.3 snapshot; release builds use the corresponding release.

Validation uses the existing Micronaut visitors and generated bean introspections and executable metadata. It does not add an annotation processor, emit annotation implementations or generate additional validation provider classes.

Validation keeps Micronaut `Argument` information through constraints, container extraction, and executable inheritance: annotations, nested generic arguments, raw types, wildcard bounds, and resolved type variables. Compile with `micronaut-validation-processor` to retain validation annotations in the normal Micronaut metadata. `ValidatedElement` marks the arguments that require traversal; unmarked branches are skipped.

== Field and Getter Access

By default, `@Introspected` selects method access. Constraints on a backing field are validated through its compatible generated property getter. Record components use their generated accessors. Ordinary bean properties and records do not require `@ReflectiveAccess`.

Selecting `accessKind = FIELD` requests direct field access. An accessible field then uses generated field access. When both `FIELD` and `METHOD` access are selected, each constrained declaration is validated against its own value. Distinct violations are retained even when their paths and messages are equal. Record component constraints are validated once during bean validation; their accessors remain available for executable return-value validation.

An inaccessible field requiring direct field access always requires the optional provider, including fields annotated with `io.micronaut.core.annotation.ReflectiveAccess`:

dependency:micronaut-validation-reflection[groupId="io.micronaut.validation"]

`@ReflectiveAccess` registers an annotated field for native images; it does not enable reflection in the default validator. Without the provider, direct access to an inaccessible field fails with a `ValidationException`. A differently typed getter cannot substitute the field's value.

The provider permits runtime discovery and invocation when generated metadata is unavailable. The system property `micronaut.validation.reflection.enabled=false` selects generated descriptions for the compatibility test profile; it does not remove modules from the classpath. The installed companion can still read fields explicitly annotated with `@ReflectiveAccess`; only a classpath without the companion proves the strict boundary. To enforce absence of runtime reflection capabilities, exclude both `micronaut-validation-reflection` and core `micronaut-reflection` from the runtime classpath.

The processor generates executable methods for constrained declarations and their overrides. Explicit `@Executable` declarations remain available. For XML mappings of otherwise unconstrained methods, annotate those methods with `@Executable`; use `@Introspected(constructors = true)` when XML or programmatic validation needs additional unconstrained constructors.

== Jakarta Signatures and Optional Modules

Jakarta operations accepting a caller-supplied `Method` or `Constructor` retain their signatures. Validation resolves their generated executable metadata. Operations that need to discover a runtime member require the reflection provider if metadata is unavailable. Ordinary Micronaut interception uses generated executable APIs.

Bootstrap and XML modules do not automatically add the reflection provider. XML mappings produce ordinary `AnnotationMetadata` and structural `Argument` values for the shared validation and descriptor implementation. Standard constraint members use the Jakarta API contracts. Runtime discovery of application annotation members, missing executable declarations, and concrete annotations for `ConstraintDescriptor.getAnnotation()` or Jakarta validator initialization require the optional reflection provider. Micronaut constraint validators consume `AnnotationValue` directly. The `micronaut-validation-jakarta` aggregate explicitly includes reflection for comprehensive Jakarta compatibility.

Ordinary group inheritance uses class assignability. Processor-visible source group interfaces extending `Default`, and source group interfaces named by constraint occurrences, receive generated introspections. Nested groups not discovered as source types can declare `@Introspected`. Other groups can declare `@Introspected` explicitly. Cascade conversion of inherited groups needs the requested group's generated hierarchy or the optional provider; a missing hierarchy produces a capability error. Duplicate requested groups are validated once.

The restricted TCK profile retains seven measured exclusions. Core processes only the first repeated `@ClassImport`, so the TCK's import containing the inner constructor fixture is ignored. Core describes the enclosing-instance parameter correctly when that fixture is imported alone. Six XML tests name private methods absent from standard introspections. The restricted profile runs 1,047 tests. The full Jakarta stack uses the optional provider and tests all 1,054 cases, including these exclusions.

== Maintainer Verification

Production compilation treats NoReflection and NullAway diagnostics as errors. Compiler fixtures also prove that generated Java cannot bypass these gates. Runtime classpath tests verify the default stack without either reflection module.

The `nativeSmokeJvm` task exercises generated member access, bootstrap, XML mappings, resource bundles, and EL on a classpath without validation, core, or EL reflection companions. It runs as part of `check`. Run the same scenario as a native executable with a GraalVM installation:

[source,bash]
----
GRAALVM_HOME=/path/to/graalvm ./gradlew :micronaut-validation:nativeSmoke
----

A validator factory captures its access provider and generated introspector during configuration. Derived validator contexts, constraint descriptors, group processing, and executable traversal keep those capabilities when the calling thread changes its context class loader.

Constraint validators registered as Micronaut beans are created through the bean context, including validators with a no-argument constructor. This preserves member injection, interceptors, and lifecycle callbacks. Unmanaged validators use their generated constructor when available.

Constraint descriptors expose typed `Pattern.Flag` and `Pattern.Flag[]` attributes, including members of custom constraints, without reflective enum lookup. The fixed Jakarta `validationAppliesTo` contract also provides typed `ConstraintTarget` values. Class-valued attributes use generated class references, and returned arrays are copied defensively. Concrete annotation instances and custom annotation-member discovery still require the optional reflection provider; this change does not generate annotation implementations.

== Generated Definitions and Runtime Fallback

The processor retains constraint-definition diagnostics, including member types and defaults, validator targets, and composition overrides. Nested compositions retain their child constraints when groups and payload are applied. Strict definition validation consumes these results without the reflection companion; invalid definitions still fail when validation requests them. Concurrent declaration checks publish only completed successes, and failed checks remain retryable.

Concrete value extractor implementations receive introspections automatically. An instance registered with `addValueExtractor` uses its generated signature, including `@ExtractedValue` and `@UnwrapByDefault`. Implementations without generated metadata can use an explicit `ValueExtractorDefinition` or the reflection companion.

Installing `micronaut-validation-reflection` preserves generated access for available executable signatures, parameter names, generic bindings, and ordinary constraint attributes. Runtime discovery supplies missing capabilities. Other enum or nested-annotation attributes need concrete runtime values; without the companion, requesting those attributes raises a `ValidationException` instead of returning strings or metadata objects with the wrong types.

The deprecated `DefaultValidatorConfiguration.getClassFromType(Type)` remains binary compatible. A `Class` argument works in the default module; parameterized signatures, wildcard bounds, and generic arrays require `micronaut-validation-reflection`. Prefer `Argument.getType()` when using generated metadata. Removal is reserved for the next major release.
