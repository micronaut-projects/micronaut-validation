This section documents breaking changes between Micronaut Validation versions:

=== Micronaut Validation 5.3.0

* Micronaut core 5.3 is the minimum supported core version.
* Default validation no longer discovers or invokes arbitrary runtime members. Ordinary properties and records retain generated getter/accessor reads. An inaccessible field requiring direct field access needs `micronaut-validation-reflection`. `@ReflectiveAccess` provides native registration but no longer authorizes reflection in the default module.
* Bootstrap no longer adds the reflection provider transitively. Applications relying on reflection fallback must add `micronaut-validation-reflection` or use `micronaut-validation-jakarta`.
* When both field and method access are selected, field and getter constraints are evaluated against their own values. The same constraint with the same attributes on a field and its getter is one constraint, as in the reference implementation: it is reported once, and `getConstraintDescriptors()` lists it once.
* The default module no longer synthesizes annotation instances through a proxy. `ConstraintDescriptor.getAnnotation()`, and the `initialize(A)` of a Jakarta `ConstraintValidator`, build the constraints of the specification and of this module with builders generated at compile time. For a constraint of the application, `micronaut-validation-processor` registers a builder when it compiles a type declaring the constraint, provided the annotation, the enum and annotation types of its members and the types enclosing them are public; for any other, list it in `@RegisterAnnotations` of Micronaut core on a type or package of the application, or add `micronaut-validation-reflection`. A Jakarta validator compiled with `micronaut-validation-processor` that keeps the default `initialize` needs no annotation instance and works without it. Micronaut validators continue to use `AnnotationValue` and the generated metadata directly.
* The deprecated `DefaultValidatorConfiguration.getClassFromType(Type)` is retained and erases a signature as before; use `Argument.getType()` for generated metadata.
* `ConstraintDescriptor.getAttributes()` returns typed values. Enum attributes without generated value support, and nested-annotation constraint attributes, require the reflection companion there; missing support fails explicitly instead of returning incorrectly typed attributes. Message interpolation does not need them: a message renders the value held in the metadata, the enum constant's name.
* A type compiled without `micronaut-validation-processor` 5.3, such as a library type or one introspected through `@Introspected(classes = ...)`, is validated with the constraints of its introspection and no separately validated super types, as before 5.3.
* Passing a `java.lang.reflect.Method` to validation needs `micronaut-validation-reflection` when Micronaut has to look that method up itself. This applies to method interception with a `ValidatorFactory` that is not Micronaut's own, such as a replaced provider, and to a custom Jakarta `ParameterNameProvider`. The default validator and the default parameter name provider use generated executable metadata and are not affected.
* An invalid constraint definition is reported by the annotation processor as a warning. Set the annotation processor option `micronaut.validation.strictConstraintDefinitions=true` to make it a compilation error.
* A constraint mapping XML file is validated against the mapping schema of its version, which the Jakarta Validation API ships: a file whose root is not `constraint-mappings` in the namespace `https://jakarta.ee/xml/ns/validation/mapping`, that repeats an element the schema allows once, or that contains an element the schema does not allow where it stands is rejected with a `ValidationException`. Such files were previously read leniently.
* Inherited group conversion needs a generated hierarchy for the requested group or the optional reflection provider. Missing capabilities produce a clear error.
* Jakarta EL interpolation requires `micronaut-validation-el` (also included by `micronaut-validation-jakarta`). Adding an EL API or implementation alone does not replace the basic interpolator.
* With `micronaut-validation-el` on the classpath its interpolator replaces the default one. An application bean that replaces `DefaultMessageInterpolator` as well must be `@Primary`.
* The default messages of `@InEnum`, `@InList`, `@NotInEnum`, `@NotInList` and `@UniqueElements` reference the value as `${validatedValue}` instead of `{validatedValue}`. Both interpolators of the module render it, a null value as the empty text, as Jakarta EL renders it; a custom `MessageInterpolator` or message bundle that matched the old template has to match the new one.
* A value extractor registered through the Jakarta Validation API (`Configuration.addValueExtractor`, `ValidatorContext.addValueExtractor`, `META-INF/services`) must mark the extracted type argument with `@ExtractedValue`, as the specification requires. A `ValueExtractor` bean of the application with a single type argument still extracts that argument without it. `MicronautValidatorContext.addValueExtractor(ValueExtractorDefinition.of(...))` registers an extractor without reading its class.
* The public constructor `ValueExtractorDefinition(Argument, ValueExtractor)` no longer selects the single type argument of a container without `@ExtractedValue`: it throws a `ValueExtractorDefinitionException`, as the specification requires for an extractor registered through its API. Mark the extracted type argument with `@ExtractedValue`, or use `ValueExtractorDefinition.of(...)` to give the index explicitly.
* With `micronaut-validation-el`, the Jakarta EL expressions written in a message template a constraint validator builds with `ConstraintValidatorContext.buildConstraintViolationWithTemplate`, or sets with `messageTemplate` of the Micronaut `ConstraintValidatorContext`, are evaluated only at the level of variables by default, as such a template may carry the validated value: variables, `${validatedValue}` included, literals, operators and `formatter.format(...)` are evaluated, and an expression reading a property, an index or a method of a value is left as written. The text of a message bundle such a template names is evaluated in full. The expressions of the message of a constraint are evaluated as before. Set `micronaut.validator.custom-violation-expressions` to `true` to evaluate the expressions of custom violations too. `formatter.format(...)` rejects a format whose width or precision is above 1024, in any template, and the expression is then left as written.
* `DefaultValidator` is closed with its bean context or validator factory, and validating with a closed validator throws a `ValidationException`.
* Validating with a `null` group throws an `IllegalArgumentException`, as the specification requires.
* `Path.toString()` renders a container element node the way the reference implementation does: a dot precedes it, and a node of a map key names the key type parameter, as in `authors[1].<list element>` and `sectionStartPages<K>[].<map key>` (previously `authors[1]<list element>` and `sectionStartPages[]<map key>`). Code that compares or parses path strings must be updated; the nodes of the path are unchanged.
* A constraint declared next to a composed constraint that composes the same constraint type is validated once for each occurrence declared, and no longer once more through the composition. Two constraint descriptors are equal when their constraint type and attributes are equal.
* `@Digits` rejects a value whose integer part has more digits than an `int` counts, such as `1E2147483647`, which it accepted before because the count overflowed. The reference implementation still accepts such a value.
* `DefaultValidator.validatedAnnotatedElement` validates a `null` value against the constraints of the element, so that `@NotNull` reports it; it returned no message for a `null` value before.
* The evaluation of a constraint annotated with `@ReportAsSingleViolation` stops on the first failure, as the Javadoc of `ReportAsSingleViolation` requires: the validator of the composed constraint runs first, and when it fails, or once a composing constraint fails, the composing constraints after it are not evaluated. A composing validator with side effects, or one that throws, is no longer called after a failure.
* The cascade into a container element follows the runtime type of the container when the element is constrained too, as it already did for an element cascaded only: with `Iterable<@NotNull @Valid Child>` holding a `List`, a violation of a child reports its index, `children[1].name` (previously `children[].name`). The constraints of the element are still validated through the extractor of the declared type.
* The rules the specification sets for the constraints of a method hierarchy are enforced when a method is validated, by method interception or the executable validation API: a method overriding or implementing another may not add parameter constraints, `@Valid` or group conversions to its parameters, parallel declarations of a method in two super types may not declare parameter constraints, and a return value may be marked `@Valid` once in the hierarchy. A violation throws a `ConstraintDeclarationException` on every validation of the method, where earlier versions validated the constraints the method declared. The rules are checked against the declarations the validator reads: the super types with a generated introspection, which `micronaut-validation-processor` 5.3 generates for a type declaring constraints or annotated with `@Introspected`. A super type without one, such as a plain interface of a library or an interface declaring no constraint, is not seen, and a method implementing it is validated with the constraints it declares, as before.
* `validateProperty` and `validateValue` check the declarations of the bean, its group conversions, and validate a property a super type redefining the default group sequence declares in that sequence, as `validate` does.
* An application context with `micronaut-validation-bootstrap` on the classpath, which `micronaut-validation-xml` and `micronaut-validation-jakarta` include, validates intercepted methods as the specification asks of a container: it applies the `executable-validation` settings of `META-INF/validation.xml`, or the defaults of the specification without it, so a constrained getter is no longer validated when it is invoked unless `@ValidateOnExecution` asks for it. Set `micronaut.validator.default-validated-executable-types` to `ALL` to validate getters as before. Without those modules nothing changes.

=== Micronaut Validation 5.0.0

- The api:validation.validator.DefaultValidator[] methods `requireNonNull(String, T)` and `requireNonEmpty(String, String)` deprecated previously and are no longer exposed as part of the public API.

- The api:validation.validator.constraints.ConstraintValidator[] method `getMessageTemplate())` and `requireNonEmpty(String, String)` deprecated previously is removed. It was unused and has no replacement.
